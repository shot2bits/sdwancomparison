## Implemented

The map requires internet access; the site list and schedule remain available if tiles fail. Browser requests use the documented tile URL, standard caching and a valid origin referrer. No offline prefetching or address geocoding is implemented.
- City-centre placement for a small explicit place directory, arbitrary buyer-entered coordinates or manual placement anywhere on the map. Unknown locations remain unplaced. All city pins are approximate; the app does not infer exact premises, carrier routes or latency.
- Named locations or aggregate site groups with counts, types, users, region, applications, cloud, retained connectivity and full own requirements. Existing unallocated site counts are reconciled as location records are added.
- Business defaults, site-type profiles and selected-record profile application. Product/feature choices use the complete existing product catalogue. Site product and feature exceptions are preserved during shared-profile updates. Bulk changes have an affected-scope preview, explicit application and undo/redo. Group profiles take precedence over business defaults; assigned selected-site profiles and local overrides remain separate. No hidden conversion of identity or endpoint products into per-site licences.
- Geographic, declared logical diagram and site-table views of the same location records. Search/filter controls, selected-site inspector, explicit save feedback, a useful next step and mobile layout. The logical diagram represents shared service relationships, not observed packet paths.
- Structured, editable location records inside the Word-like Living RFP. Saving a site there updates the map, effective products, combined comparison and compiled schedule. Business-wide product edits in the existing RFP controls also update inherited defaults, preserving group and site exceptions. The compiled location requirement remains fully visible but read-only; edit the structured records rather than attempting to infer topology from arbitrary text edits.
- The existing public Neon-backed comparison of all 30 providers, evidence findings, sector references, source links, source qualifications and full original-record access. Matches use a union of effective product/feature needs and a full location schedule as a buyer requirement. Exact site delivery and site-specific fulfilment need supplier confirmation; this is not a new per-address ranking model.
- Reviewed CSV import with quoted/multiline values and complete original columns retained in each source record. Site CSV export includes original source values. JSON backups contain the estate and the full connected core project, including existing conversation and buying-workspace data. Backup restore passes through the existing core validation endpoint. The new route has separate browser save keys so normal context-preview saves are preserved. Site form drafts stay available while moving between locations; Save project applies valid pending site edits, while backups also retain pending drafts. Saved sector selections restore only after their catalogue definitions have loaded.
- A manual audit-finding review that retains source/date/original finding and adds a buyer-accepted requirement to chosen locations. No network discovery or automated audit-product connector is claimed.
- Existing introduction, original context map, supporting page sections, Living RFP, full research, question banks, buyer checklists, provider comparison, buying workspace and private supplier conversation prototype remain present. The original workspace is in an expandable section below the new map. Existing content has not been deleted.

## Boundaries

The structured location model remains a local prototype extension. Its compiled schedule enters the existing core RFP as a complete buyer requirement; JSON location backup is the lossless structured format. Arbitrary prose edits to core document totals or requirements cannot reliably infer site allocations, and are not represented as automatic topology extraction. Future production work needs a first-class validated site model in the main project contract and explicit conflict handling for aggregate edits.

Site metadata is not yet a production database migration. Supplier designs, live audit imports, live identity/Teams/WhatsApp, invitations, bids and publication remain integration work; existing safe local conversation previews are retained. Unknown fields remain unknown. No capabilities, geographic delivery or security posture are verified merely by a map pin.

The existing core validation limit permits 20,000 characters per buyer requirement. The mockup rejects a compiled location schedule above 19,500 characters explicitly rather than shortening it. Original CSV input remains available when a proposed import is rejected. A later production location schedule must be stored/exported as structured records rather than compressed into this single core field. Location validation permits up to 1,000 records subject to that document limit; aggregate groups can describe larger estates without inventing individual addresses. Backups/imports have a visible 5 MB limit.

OpenStreetMap community tiles are used only for a modest private preview. Choose an appropriate hosted tile service or self-hosted tiles before a public release. Leaflet's licence is retained under `vendor/leaflet-LICENSE`. Tile permissions are added only to the new route's CSP; original preview CSP is retained. Keep map attribution visible.

## Connected to the existing Netify AI on 12 November 2026

No Vercel configuration, deployment, production project or Neon record was changed. The existing route computes and returns field proposals; it does not create a saved marketplace project, message suppliers or publish an opportunity.

`context-existing-ai.ts` sends bounded office-source parts within the existing API's 4,000-character request boundary. The existing named-location validator caps each list at eight. The adapter detects a result reaching that cap and reads smaller complete source parts until the list is below the cap; it also supports a smaller-part retry for a model parsing/timeout failure. Failed reads abort the other work and return no partial import. Source parts are lossless, word-boundary-aware, and limited to two concurrent requests. Only `estate.namedLocations` proposals are consumed; user counts, products, budgets and other returned fields cannot become project facts through this connection. A small dense eight-name list is covered by regression tests.

The company-page reader identifies an explicit office/location section when available, or main page content otherwise, to avoid treating navigation and product menus as company requirements. It keeps the complete extracted page separately. Block spacing is preserved so city headings are not joined to adjacent interface words. The review explicitly explains the focused analysis. Candidate cities must occur in their corresponding source part, with exact evidence copied from the source. Evidence stops at the next named city, avoiding an adjacent office's address or qualification being attached to the wrong record. Customer/negated mentions and unknown names cannot create guessed sites. Mailing-only/virtual addresses remain in the findings but are unchecked by default with an explanation. Ambiguous city matches require the buyer to choose the intended place.
