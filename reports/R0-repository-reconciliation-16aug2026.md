## 4. Existing architecture map

Two structurally separate document/publish systems coexist and **do not communicate**:

- **New — Living Procurement Document.** `ProjectDesk.tsx` (buyer-facing canvas, mounted at the canonical `/home/` route) → `compileProcurementDocument()` in `procurement-document.ts` (pure, client-invoked compiler; clauses, gates, weights, architecture, outline, best-next-decisions) → sector packs (`sector/packs.ts`/`derive.ts`, exactly `healthcare` and `manufacturing`) supply optional governed suggestions with accept/decline/reverse lifecycle (row 6). This system is **purely client-side and never persisted**; it never reaches publish, snapshot, or export.
- **Old — RFP document pipeline.** `RfpBuilder.tsx` (a separate, older builder surface, reachable at `/rfp-builder/[id]`) → `rfp_sections`/`buyer` fields on `ProjectDetails` → `executePublish()` (`rfp-publish.ts:478-823`) → `PublishedSnapshot` (`published-snapshot.ts`, genuinely persisted, versioned, content-hashed) → export route (`preview/download/route.ts`). This is the pipeline that actually gets saved, published, frozen, and exported.

Row 8's pre-publish leak and row 12's second print path both live entirely in this older pipeline's surface (`RfpBuilder.tsx` and its supporting routes/components), not in the newer canvas.

Supporting systems: auth/session (`src/lib/auth.ts`, cookie-based), access control (`src/lib/rfp-access.ts`'s `requireRfpOwner`, lines 50-64), consent (`ProjectDetails.consents`, server-minted, append-only, enforced server-side by `hasPublishConsent`/`project-machine.ts:113-119`), storage (`src/lib/rfp-store.ts`, Upstash-REST-compatible KV).

## 9. Security, permission and audit-boundary findings

- **Row 8 (pre-publish identity boundary)** is the standout finding: a real, exploitable, pre-publish vendor-identity and supplier-contact leak in `RfpBuilder.tsx` and its supporting routes, on a boundary the brief calls a release-blocking invariant, uncaught by the fixture meant to police it.
- **MCP endpoint has no transport-level auth** and wide-open CORS (row 14); per-tool gating is real but the absence of any auth at the transport layer is itself worth Robert's attention independent of the "Later" documentation gap.
- **Weak token generation**: every secret in the system (manage/share/connection/session/magic-link tokens) is generated by `newId()` (`rfp-store.ts:82-84`) = `Date.now().toString(36) + Math.random().toString(36).slice(2,8)` — not a CSPRNG, roughly 31 bits of true randomness. No confirmed exploit path was found, but it is a structural weakness worth flagging.
- Consent is genuinely server-enforced (not client-spoofable): server mints the consent record text itself, `hasPublishConsent` is checked server-side, history is append-only (`project-machine.ts`).
- Owner-gating (`requireRfpOwner`) is correctly applied on the routes I checked outside of the row 8 leak; the leak is specifically a missing *publish-state* check layered on top of otherwise-correct ownership checks, not a broken ownership boundary.
