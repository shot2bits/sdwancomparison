# Support email alerts — 8 November 2026

User requested Resend emails to support@netify.com for project publication and supplier approval requests. Existing Resend transport retained. Recipient is fixed to the requested support inbox; no supplier invitation, automatic approval or new administrator permission.

An immutable notification intent is saved before the source snapshot/claim is committed. Delivery checks the matching published snapshot or pending claim, saves its payload, and requires a successful Resend receipt. A protected five-minute Vercel cron retries queued work. Repeat publication and identical pending claims do not resend. Timeouts/receipt-write crashes reuse the same Resend idempotency key and frozen payload. After 23 hours from first attempt, ambiguous work stays visible for delivery review instead of risking a duplicate outside Resend's 24-hour deduplication window. Admin and daily digest show pending/review counts; existing verified bounce webhook can correlate admin alerts and expose a recorded support inbox delivery failure. No historical backlog is mailed automatically.

Project emails link to the authenticated read-only admin project; supplier emails link to Supplier approvals. No bearer credentials, personal buyer contacts or full requirements in the team email. The legacy standalone opportunity creation path also queues an alert. Buyer confirmation emails remain independent.

Local validation: TypeScript and scoped ESLint pass; real Redis notification regression passes rejection, timeout, receipt persistence failure, idempotency, no key, uncommitted event gating, resolved approval cancellation and cron authentication. Real Redis Studio route suite checks RFI/RFP actual publication hooks, support recipient and admin link, no private brief/token, replay suppression and supplier claim notification. Actual AdminClient login/approval/retry/expiry tests pass. Hosted acceptance and production identity will be recorded after verification.
