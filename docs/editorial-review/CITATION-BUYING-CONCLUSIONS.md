# Buying conclusions for actual editorial review

Status: drafts only. Not published; no human approval has been invented.

## 1. Ten UK sites, no internal network team

**Proposed conclusion:** Begin by comparing a carrier-managed route such as BT with a managed-network route such as Aryaka. The decision is not which has the most feature ticks: it is which organisation accepts responsibility for access circuits, branch equipment, security policy, changes and incident escalation. Add a platform-plus-MSP route only when a named operator can quote those responsibilities together.

**Assumptions:** UK sites; managed operations required; no existing platform requirement supplied. These are routes to investigate, not a personalised recommendation or a claim that only these suppliers qualify.

**Evidence:** BT describes its Fortinet-based managed SD-WAN service (https://business.bt.com/content/dam/bt-business/pdfs/networks-cloud-digital-services/sd-wan/bt-secure-sd-wan-datasheet.pdf). Aryaka describes managed, co-managed and self-managed delivery (https://www.aryaka.com/use-cases/network-and-security-convergence/).

**What could reverse the conclusion:** site availability, minimum commercial scope, current contracts, migration risk, a required security platform or unavailable support commitments. Ask both suppliers for a responsibility matrix and an itemised proposal for the same site list. Public product evidence does not establish the price or supplier acceptance of a ten-site project.

## 2. An existing security platform the buyer wants to retain

**Proposed conclusion:** Compare retaining the existing security platform and sourcing compatible managed networking against replacing both with a converged offering such as Cato. Replacement needs a business case that includes remaining licences, policy migration and operational changes; a shorter feature list alone does not justify it.

**Assumptions:** The current platform meets the buyer’s requirements and replacement is optional. Do not name a compatible integration until its exact products and supported design are evidenced.

**Evidence:** Cato’s platform model (https://www.catonetworks.com/platform/); vendor-specific integration and contract evidence must be attached for whichever existing platform is supplied in the brief. This draft needs that additional case-specific evidence before publication.

**What could reverse the conclusion:** an unsupported integration, duplicated inspection, traffic-routing constraints, contract exit costs or an essential existing policy that cannot be reproduced. Request a reference architecture and costed migration plan for each route.

## 3. One accountable supplier for connectivity and overlay

**Proposed conclusion:** Compare a carrier-managed option, illustrated by BT, with a managed SD-WAN option from GTT. Require both to identify the contracting entity, access-circuit suppliers, service operator and incident owner. A supplier selling circuits and SD-WAN is not proof of one SLA or one contractual responsibility for every fault.

**Assumptions:** The buyer prioritises accountability across connectivity and managed networking. Supplier scope and site coverage remain unconfirmed.

**Evidence:** BT managed SD-WAN datasheet above; GTT managed SD-WAN service (https://www.gtt.net/services/secure-networking/managed-sd-wan/).

**What could reverse the conclusion:** excluded access circuits, local delivery partners, separate security contracts, different fault demarcations or an unacceptable change process. Ask for itemised underlay/overlay costs, exclusions and an escalation matrix before comparing totals.
